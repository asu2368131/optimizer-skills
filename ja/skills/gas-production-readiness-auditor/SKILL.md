# GAS 本番稼働準備状況監査

GAS プロジェクトを、性能、アーキテクチャ（拡張性）、保守性、信頼性、データ整合性、運用性・可観測性、セキュリティ、開発者体験の 8 軸で監査します。

単なる速度改善ではありません。すべての判断では「1 年後にも安全に変更できるか（保守性）」と「壊れたときに復旧できるか（運用準備）」を問います。高速に成功する経路より、復旧できる失敗経路を重視してください。

> このフレームワークは GAS の本番運用経験、運用上の教訓、設計ヒューリスティックの集約です。Google の公式標準ではありません。規模、リスク、要件に応じて技術的に判断してください。

# 基本原則

```text
原則 1: 最速の API は、呼び出さない API である
原則 2: 処理を 100 回高速に実行するより、100 回実行しない方がよい
原則 3: 良い GAS は速い GAS ではない。1 年後にも安全に変更できる GAS である
原則 4: 成功ケースではなく失敗ケースを設計する
原則 5: LockService は同時実行を防ぎ、べき等性は再実行を防ぐ。両方が必要である
原則 6: 「成功する処理」より「壊れても復旧できる処理」を優先する
原則 7: 複雑さは無料ではない。規模とリスクに見合う最小の設計を選ぶ
```

原則 1〜3 は性能・保守性、原則 4〜6 は運用準備、原則 7 は過剰設計を防ぐ基準です。すべてを Repository 化、TypeScript 化、状態機械化したくなったら、原則 7 に戻ってください。

# 出力形式

監査結果は必ず次の構成にします。

```text
## 総合スコア
## 本番稼働準備判定
## カテゴリ別スコア
## 検出事項（重大度別）
## 改善提案
## 優先度付きアクション一覧
## リファクタリング案（変更前／変更後）
```

## 採点基準

```text
A+  95〜100
A   90〜94
B   80〜89
C   70〜79
D   60〜69
F    0〜59
```

各カテゴリも同じ尺度で採点します。

## 重大度の決め方

減点幅ではなく「安全に本番へ出荷できるか」で分類します。Critical が 1 件でもあればスコアにかかわらず出荷不可です。F はスコア、Critical は出荷可否であり、別の軸です。

```text
Critical  本番出荷不可。データ破壊、情報漏えい、または確実な障害につながる
High      早期に修正必須。障害時に復旧できない、または整合性が壊れる
Medium    計画的に修正。影響範囲は限定的だが、放置すると技術的負債になる
Low       余裕があれば修正。実害は小さい
Info      記録のみ。許容できる設計判断の場合がある
```

例:

```text
Critical : API キーのハードコード / LockService 不使用 / 「自分として実行」かつ「全員がアクセス可」の Web アプリ / べき等性なしの再送処理
High     : チェックポイントなし / リトライなし / 部分失敗を未処理 / 成功・失敗だけの二値ステータス
Medium   : row[14] への直接参照 / getLastRow 依存 / 設定値を毎回再読込
Low      : Logger.log の過剰使用 / 不明瞭な命名
```

## 本番稼働準備判定

総合スコアとは別に、本番に適しているかを明示します。

```text
READY                  本番稼働可能
READY WITH CONDITIONS  指定条件を満たせば本番稼働可能
NOT READY              本番稼働不可（阻害事項の解消が必要）
```

Critical が 1 件以上なら `NOT READY`、High のみなら `READY WITH CONDITIONS`、どちらもなければ `READY` です。

# 監査カテゴリ

## 性能

### 1. セル単位の API アクセス

`getValue`/`setValue`/`getValues`/`setValues`/`flush` の呼び出し回数を数えます。セル単位のアクセスを避け、必要な範囲だけを一括取得します。`getDataRange` の使用と API 呼び出し総数も確認します。

悪い例:
```javascript
for (const row of rows) {
  range.getValue();
}
```
推奨例:
```javascript
const data = sheet
  .getRange(startRow, startColumn, rowCount, columnCount)
  .getValues();
```

`getDataRange().getValues()` は便利ですが、データ量が予測できない場合は #6 の分割処理・メモリ問題につながります。可能な限り明示的な範囲を指定します。

### 2. 全件読込・処理・全件書込

「全件読込 → 処理 → 全件書込」の順序を守っているか確認します。読込と書込を交互に行う実装は禁止です。

### 3. イベントオブジェクトの使用

`onEdit`/`onChange`/`onOpen`/`onFormSubmit` がイベントオブジェクトを使うか確認します。`e.value`/`e.oldValue`/`e.range` を無視し、`sheet.getRange(...).getValue()` で再取得している場合は警告します。

### 4. キャッシュ

`CacheService` の使用と、API 応答・設定値・参照データがキャッシュ候補かを確認します。容量制限、最大 6 時間の TTL、退避により内容は**予告なく消える**ため、ロック・排他状態、処理済みフラグ、トランザクション、金銭データを入れてはいけません。失われると困るものはキャッシュせず、PropertiesService または専用シートに永続化します。

### 5. クォータと実行時間制限

サービス別の日次クォータ（Gmail/Drive/UrlFetch/Calendar）、1 実行あたりの時間、アカウント・プロジェクト上限を独立して評価します。Consumer、Google Workspace とも 1 実行の上限は **6 分**です。カスタム関数は 30 秒で、Workspace アドオンには固有の制限があります。

```text
使用率 50% 未満  安全
使用率 50〜75%   警告（データ増加時のリスク領域）
使用率 75〜90%   High（早めに分割する）
使用率 90% 超    Critical（タイムアウト寸前）

Utilities.sleep の上限        5 分
同時実行数                    ユーザーあたり 30
トリガー実行時間の日次合計    Consumer: 90 分 / Google Workspace: 6 時間
```

上限が不明なら保守的に 6 分を使います。高頻度の時間主導トリガーは日次実行時間を先に使い切るため、対象アカウント種別に基づき見積もります。

### 6. 分割処理とチェックポイント

`PropertiesService` に再開位置を保存するチェックポイント付き分割処理を確認します。`getDataRange().getValues()` で数万行を一度に読む実装は、`getRange(startRow, 1, chunkSize, cols)` による分割取得を評価します。初期の目安は 100〜1,000 件ですが、列数、API 回数、1 件の処理時間、クォータ消費に合わせて調整します。

## アーキテクチャ

### 7. 責務分離

`main()` が読込・検証・処理・保存をすべて担っていないか確認します。`load()` / `validate()` / `process()` / `save()` のように機能ごとに分割します。

### 8. レイヤーと依存方向

`UI → Controller → Service → Repository → Google API` の一方向の依存を推奨します。Repository に業務ロジックがある、Service が UI を参照するなど、下位レイヤーが上位を参照する逆方向・循環依存を指摘します。

## 保守性

### 9. コード構成と構造的負債

単一ファイルの肥大化（例: 3,000 行の Code.gs）を警告し、`Config.gs`、`Main.gs`、`Sheets.gs`、`Drive.gs`、`Utils.gs` などへ分割を提案します。関数長と、3 か所以上にある約 10 行以上のコピー＆ペーストも検出します。これは「半年後に誰かが安全に変更できるか」の軸です。

```text
関数長 100 行超: 警告 / 300 行超: High / 500 行超: Critical
```

### 10. 命名

関数・変数・ファイル名が妥当か確認します。`test()` のような無意味な名前を避け、`generateInvoicePdf()` のように意図が分かる名前を推奨します。

### 11. 定数

シート名や ID のハードコードを検出し、`const SHEET_MAIN = "..."` のような定数定義を推奨します。

### 12. 列名によるアクセス

`row[14]` のようなインデックス直接参照は禁止です。列の挿入・移動で壊れます。ヘッダー行を `{columnName: index}` のマップにし、`COL_EMAIL` や `employee.email` のように名前でアクセスします。

## 信頼性と可観測性

### 13. エラー処理

`try/catch` の有無を確認します。`catch(e){}` のようにエラーを握りつぶす実装は重大な警告です。失敗した操作、対象 ID、入力値、`e.stack` を記録します。

### 14. 復旧とチェックポイント

長時間処理が中断した後に再開できるよう、処理状態を `PropertiesService` などへ永続化しているか確認します。

### 15. 構造化ログ

`Logger.log()` 自体は禁止ではありません。問題は大量の連続ログ、文字列連結のログ、本番で実行ログだけを記録先にすることです。`console` / Cloud Logging / Error Reporting に出力し、検索・集計できる構造化ログを優先します。

```javascript
// 悪い例
console.log('import failed ' + messageId);

// 推奨例
console.log({ level: 'ERROR', event: 'IMPORT_FAILED', messageId, parser, error: e.stack });
```

`INFO` / `WARN` / `ERROR` を区別し、失敗ログに対象 ID と入力値を含めます。

### 16. デバッグ容易性

デバッグがログだけに依存していないか、実際のデバッガーを使える構成かを確認します。

## スプレッドシート数式と UI

### 17. 数式と GAS

`ARRAYFORMULA`/`OFFSET`/`VLOOKUP`/`IMPORTRANGE` の使用を確認し、GAS の処理を数式（名前付き関数、ArrayFormula）に置き換えられないか検討します。

### 18. UI の表面

`Ui.prompt()` の多用を警告し、Sidebar または Dialog を推奨します。`<?!= include() ?>` による SSR 依存も検出します。

### 19. 規模に見合うフロントエンド

SPA、ルーター、TypeScript、テストフレームワークがないことだけを理由に小規模 GAS を減点してはいけません（原則 7）。規模に応じて、画面遷移、`google.script.run` の Promise ラッパー、TypeScript、Jest/Vitest を確認します。

## 開発者体験

### 20. ツールチェーンとローカル開発

`clasp` によるローカル開発と、規模に見合う ESLint、Prettier、Vite、TypeScript の採用を確認します。

### 21. バージョン管理

Git によるバージョン管理を確認します。本番環境だけで運用している場合は重大な警告です。

### 22. デプロイの健全性

Dev/Stage/Prod の分離、最新コードの反映、`/exec`（本番）と `/dev`（最新コード、権限が必要）の混同、デプロイ版と説明の管理を確認します。

## セキュリティ

### 23. 秘密情報

API キー、トークン、パスワードのハードコードは禁止です。PropertiesService などコード外のストアへ移しますが、スクリプト編集者は読めるため、実行 ID、編集者、アクセス範囲を合わせて確認します。広く共有されたスプレッドシートに紐づくスクリプトでは実質平文に近いため、プロジェクト分離またはアクセス制限を検討します。高機密の認証情報には Google Cloud Secret Manager などを検討します。

### 24. OAuth スコープの最小化

`appsscript.json` の `oauthScopes` とコードが実際に使う権限を照合し、過剰・未使用のスコープを指摘します。説明できないスコープ増加は Medium〜High です。

### 25. Web アプリの実行 ID

「自分として実行」かつ「全員がアクセス可」は、訪問者がデプロイ者の権限で Spreadsheet/Drive/Gmail を操作できる情報漏えいリスクです。意図的な場合を除き重大な警告とします。

### 26. OAuth の細分化された同意

利用者は一部スコープを拒否できます。インストール型トリガーは `ScriptApp.requireScopes(ScriptApp.AuthMode.FULL, [...])` で作成時に権限を検証します。Web アプリ／アドオンは実行途中で落ちる前に不足を検出し、`onOpen`/`onEdit` は `e.authMode` の `NONE` / `LIMITED` を考慮します。不足を握りつぶして途中まで処理する実装は High です。

## GAS 固有の落とし穴

### 27. 同時実行と LockService

`onEdit`/`onFormSubmit`/Web アプリなど、同時実行され得る処理を特定します。**共有状態を更新する**処理で競合、重複実行、行ずれが起き得るなら、`LockService`（`getScriptLock`/`getDocumentLock`）または同等の排他設計がないことは Critical です。読み取り専用、または実行ごとに書込先が独立する処理にはロックを要求しません。

### 28. ループ内の appendRow

`appendRow()` を数百〜数千回のループで呼んでいないか確認します。バッファして最後に 1 回の `setValues()` で一括書込します。

### 29. トリガーのコンテキストと認可

`Session.getActiveUser().getEmail()` はトリガーや Web アプリで空文字列になることがあります。ユーザー識別では `Session.getEffectiveUser()` またはフォーム回答者情報を使います。単純トリガーは `LIMITED` または `NONE` で動作し、`UrlFetchApp`/`GmailApp`/`DriveApp` など認可が必要なサービスを呼べません。必要ならインストール型トリガーへ移行し、手動・時間主導・Web アプリの実行差を特定します。

### 30. getLastRow / getLastColumn

`getLastRow()` は古いデータ、残った数式、書式だけのセルを拾うことがあります。「ヘッダー行数 + 実レコード数」としてデータ範囲を明示管理します。

### 31. 空セルは null ではなく ""

空セルは `null` ではなく `""` を返します。`value === null` や `!value` 前提の分岐を、`=== ""` または明示的な空値判定に修正します。

### 32. タイムゾーン

`new Date()`、`Session.getScriptTimeZone()`、スプレッドシートのタイムゾーンが一致する前提を確認します。`Utilities.formatDate(date, tz, format)` で明示し、`appsscript.json` の `timeZone` も確認します。

### 33. マニフェスト監査

`appsscript.json` をコードと独立して確認します。

```text
oauthScopes      コードが実際に使う権限と一致するか（#24）
timeZone         日付処理とスプレッドシートに一致するか（#32）
runtimeVersion   V8 か（#34）
exceptionLogging STACKDRIVER か（#15）
dependencies     未使用の高度なサービスやライブラリがないか
webapp / addOn   access / executeAs は意図どおりか（#25）
```

### 34. V8 と旧式構文

ランタイムが V8 か確認します。`var` 中心のコード、関数式コールバック、Rhino 時代の回避策を調べ、`const`/`let`/アロー関数/テンプレートリテラル/分割代入への更新を検討します。

### 35. HtmlService の viewport とモバイル対応

HTML 内の `<meta name="viewport">` は HtmlService で無視されることがあります。`doGet` で、すべての HTML 出力へ `.addMetaTag('viewport', 'width=device-width, initial-scale=1')` を付けます。16px 未満の input フォント、44px 未満のタップ領域、ソフトウェアキーボードを妨げる `position: fixed` も確認します。

### 36. HtmlService の CSP と CDN

外部 CDN の `<script src>` や CSS への強い依存を確認します。iframe サンドボックス制約や CDN 廃止のリスクを評価し、重要ライブラリはローカル同梱またはフォールバックを設けます。

### 37. UrlFetchApp の耐障害性とリトライ安全性

`UrlFetchApp.fetch()` は 429/500/タイムアウトで失敗し得ます。`muteHttpExceptions: true`、ステータスコード確認、`Utilities.sleep` による指数バックオフを要求します。

```text
429 / 502 / 503 / 504  → リトライ
408 / タイムアウト   → リトライ
400 / 401 / 403 / 404 → リトライしない（入力・認可の問題）
Retry-After ヘッダー  → あれば指定秒数待機
```

待機と再試行で 6 分を使い切らないよう設計します。POST は受信側のべき等性キーまたは存在確認がなければ、失敗後の再試行で重複登録を起こします（#44）。

### 38. PropertiesService の容量

巨大な JSON を保存していないか確認します。上限は値ごとに約 9KB、合計約 500KB であり、データベースではありません。増大する構造化データには CacheService、別シート、Firestore などを検討します。

## データと運用上の依存関係

### 39. 複数シート間の依存

`SheetA → SheetB → QUERY/IMPORTRANGE → GAS` のような暗黙的依存を確認します。依存グラフを図または一覧で文書化し、元シートの列変更の波及先を特定します。

### 40. 名前による Drive 検索

`DriveApp.getFilesByName()`/`getFoldersByName()` の多用を警告します。同名ファイル、大量ファイル、共有ドライブで誤一致するため、`getFileById` で直接参照します。

### 41. トリガーの増殖

同じ関数への重複した時間主導トリガー、対象関数が消えた孤立トリガー、不要な編集トリガーの蓄積を検出し、`ScriptApp.getProjectTriggers()` で監査します。

### 42. Google サービスの境界

1 関数が Spreadsheet、Gmail、Drive、Calendar を一度に操作していないか確認します。各サービスをラッパー関数に分け、クォータ、権限、失敗単位を分離します。

### 43. AI 生成コードのにおい

`catch(e){}`、未使用の Utils 関数、デッドコード、行数だけを増やすコメント、実装が 1 つしかない抽象化を検出します。削除・統合の観点からレビューします。

## 信頼性と運用準備

GAS 運用で多い障害は「遅い」ことではなく、「重複処理」と「壊れても誰も気付かない」ことです。外部連携、トリガー、Web アプリがある場合、成功経路だけでなく失敗・再実行経路を次の項目で確認します。

### 44. べき等性と重複イベント

同じ Message ID / Transaction ID / Response ID が再送されても結果が変わらないか確認します。Gmail トリガーの再実行、Webhook の再送、FormSubmit の重複は日常的に起こります。処理済み ID（`messageId`/`threadId`/`transactionId`）を PropertiesService または専用シートに永続化し、処理前に照合します。べき等性キーのない書込・送信操作は Critical です。

### 45. 宛先間のデータ整合性

Spreadsheet + Notion、Sheet A + Sheet B のように複数宛先をまたぐ処理で部分失敗を扱うか確認します。「Spreadsheet 保存成功 → Notion 保存失敗」で不整合を放置する設計は High です。ロールバック、補償処理、または後で追随同期する `unsynced` フラグを確認します。

### 46. 状態機械

長時間処理、外部連携、再開可能なバッチでは、レコード状態を `NEW` / `PROCESSING` / `SUCCESS` / `FAILED` / `RETRY` のように明示します。成功・失敗だけの二値では、途中停止と未開始を区別できず再開できません。小規模な一度きりの処理に 5 状態機械を要求してはいけません（原則 7）。

### 47. 失敗レコードのキュー

`FAILED_JOBS` / `FAILED_EMAILS` / `FAILED_IMPORTS` のようなフォールバックシートに、失敗した入力、対象 ID、エラー、発生時刻を残し、後で再処理できるかを確認します。失敗が `console.log` だけに流れて消えるなら High です。

### 48. トリガーの所有者

インストール型トリガーは**作成したユーザーの権限で実行**されます。個人アカウントの作成者が異動、退職、削除されるとトリガーは停止します。各トリガーの所有者、変更・再作成手順、定期的な本番処理が特定個人に紐付いていないことを確認します。企業運用では、所有者が不明な定期トリガーは High です。

### 49. 共同所有とバス係数

本番 GAS が個人の My Drive にしかないか確認します。共有ドライブまたは組織管理下にあり、複数人が編集・デプロイできる、すなわちバス係数が 1 より大きい状態を推奨します。引継ぎ手順のない個人所有は High です。

## HtmlService テンプレートと Web アプリの画面遷移

ページは表示され、大半のリンクも動くのに、フィルター付きパス、非 ASCII 値、フォーム送信だけが壊れる静かな障害があります。例外を出さないためスモークテストを通り抜けます。`createTemplateFromFile` で作る HtmlService Web アプリまたは Sidebar では必ず確認します。

### 50. `<?= ?>` 内の文字列連結で作るクエリ文字列

`href` 内の `<?= cond ? '&key=' + encodeURIComponent(v) : '' ?>` は壊れます。HtmlService は URL コンテキストのスクリプトレット出力をエスケープするため、出力した `&` は `%26`、`=` は `%3D` になります。区切りの `&` と `=` は**テンプレート上のリテラル文字列**にし、スクリプトレットは `encodeURIComponent` 済みの値または `''` だけを出力します。

```html
&category=<?= cond ? encodeURIComponent(v) : '' ?>
```

フィルターなしでは動き、カテゴリ・タグ・検索語・フラグが有効なときだけ壊れるのが典型です。画面遷移とレコード検索を静かに壊すため High です。

### 51. `<? ?>` スクリプトレットは JavaScript を解析しない

テンプレートエンジンは次のリテラル `?>` までを走査するだけで、JavaScript を理解しません。コメント内を含め、スクリプトレット内に `<?`、`<?=`、`?>` を置いてはいけません。説明はスクリプトレット外の HTML コメント `<!-- -->` に置きます。

### 52. Web アプリの `e.parameter` と非 ASCII 値

公開した `/exec` URL では、非 ASCII のクエリ値が再エンコードされ、`e.parameter.x` が `%E4%B8%BB%E8%8F%9C` のように未デコードで届くことがあります。ASCII パラメーターは影響を受けません。`doGet` で、値が `%XX` を含むときだけ `try/catch` で保護して各テキストパラメーターを一度デコードし、新しいパラメーターも同じヘルパーを通します。影響範囲に応じて Medium〜High です。

### 53. HtmlService 内のフォームとリンクには絶対 URL を指定する

`action` のない `<form method="get">` はサンドボックス iframe URL へ送信され、空白ページになります。`action` には `ScriptApp.getService().getUrl()` で得たデプロイ URL を設定します。相対 `<a href>` も iframe URL を基準に解決されるため、画面遷移リンクは Web アプリの絶対 URL にします。`<base target="_top">` の存在も確認します。

# 監査の進め方

1. 対象プロジェクトのファイル構成、行数、トリガー定義を把握する。
2. 最大のボトルネック源である性能（#1〜6）を最初に確認する。
3. アーキテクチャと保守性（#7〜12）を確認する。
4. 信頼性と可観測性（#13〜16）を確認する。
5. 数式、UI、フロントエンド、開発者体験、セキュリティ、GAS 固有の落とし穴、HtmlService、データ・運用依存を実際のプロジェクトに応じて確認する。該当しないカテゴリは採点対象外と明記する。
6. 信頼性と運用準備（#44〜49）、#27（ロック）、#37（リトライ安全性）を確認する。
7. 出力形式に従い、スコア、重大度別の検出事項、本番稼働準備判定、改善提案をまとめる。推奨事項は規模とリスクに見合う最小限にする（原則 7）。
